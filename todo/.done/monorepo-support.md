# Monorepo Support

Status: Proposed
Priority: High

## Context

rlsbl manages releases for single-project repos. Many real-world projects are monorepos containing multiple independently versioned packages across different ecosystems (e.g., a cross-platform library shipping Python, Swift, Kotlin, TypeScript, and a spec -- each with its own version, changelog, CI, and release cadence).

The `release.py` command has partial infrastructure for `--scope` (scoped version dirs, scoped changelog lookup, commit path prefixing), but it is dead code: no target declares `scope = "subdir"`, all targets ignore the `name` parameter in `tag_format()`, and `scaffold` has zero scope awareness.

This TODO proposes first-class monorepo support via a `rlsbl monorepo` command family, a `.rlsbl-monorepo/` workspace config directory, and a router-based CI architecture.

## Design Principles

1. **Each project is fully standalone.** A monorepo project is identical to a single-repo project. Same `.rlsbl/config.json`, same `CHANGELOG.md`, same CI workflow YAML. If you extract it to its own repo, you move its files and everything works with zero changes.

2. **The monorepo layer is additive.** It adds workspace coordination (manifest, tag prefixing, CI routing) on top of standalone projects. It never modifies how individual projects work internally.

3. **No special target modes.** Targets don't need to know about monorepos. The workspace layer handles tag prefixing and CI routing externally. Targets remain simple: detect, read version, write version, build, publish.

## Architecture

### Directory Structure

```
my-monorepo/
  .rlsbl-monorepo/
    workspace.json          # manifest listing all projects
  .github/
    workflows/
      ci-router.yml         # generated: dispatches to per-project CIs
      tooling-ci.yml        # copied from tooling/.github/workflows/ci.yml
      tooling-publish.yml   # copied from tooling/.github/workflows/publish.yml
      ios-ci.yml            # copied from ios/.github/workflows/ci.yml
      ...
  tooling/
    .rlsbl/config.json      # standard per-project config
    .github/workflows/
      ci.yml                # source-of-truth CI workflow (reusable format)
      publish.yml           # source-of-truth publish workflow
    CHANGELOG.md
    pyproject.toml
    src/
  ios/
    .rlsbl/config.json
    .github/workflows/
      ci.yml
      publish.yml
    CHANGELOG.md
    Package.swift
    Sources/
  web/packages/core/
    .rlsbl/config.json
    .github/workflows/
      ci.yml
      publish.yml
    CHANGELOG.md
    package.json
    src/
```

### Workspace Manifest

`.rlsbl-monorepo/workspace.json`:

```json
{
  "projects": [
    { "path": "tooling", "name": "tooling" },
    { "path": "ios", "name": "ios" },
    { "path": "web/packages/core", "name": "core" },
    { "path": "web/packages/svelte", "name": "svelte" },
    { "path": "android", "name": "android" },
    { "path": "spec", "name": "spec" }
  ]
}
```

- `path`: relative path from repo root to the project directory.
- `name`: short name used for tag prefixes and CI workflow naming. Defaults to the last path component if omitted.
- The target is NOT declared here -- it's auto-detected from each project's own files (pyproject.toml -> pypi, Package.swift -> swift, etc.) or declared in the project's own `.rlsbl/config.json`.

### Tag Format

Scoped tags use `name@vX.Y.Z`:

- `tooling@v1.2.0`
- `ios@v0.8.1`
- `core@v1.0.0`

This is the npm/lerna/changesets convention. The `@` unambiguously separates the project name from the version. `name-vX.Y.Z` is ambiguous (is `my-lib-v1.0.0` project `my-lib` or project `my`?). `name/vX.Y.Z` causes issues with git ref parsing.

Implementation: the monorepo layer wraps `tag_format()` calls, prepending the project name. Individual targets remain unchanged -- they still return `v{version}`, and the workspace layer prefixes it.

### CI Architecture

**Per-project CI workflows** live next to each project in `{project}/.github/workflows/ci.yml`. These are full GitHub Actions reusable workflows (`workflow_call` trigger). They define how to build and test that specific project.

Example (`tooling/.github/workflows/ci.yml`):
```yaml
name: Tooling CI
on:
  workflow_call:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
      - run: cd tooling && uv run pytest
```

**The router** (`.github/workflows/ci-router.yml`) is auto-generated by `rlsbl monorepo sync`. It detects which paths changed and dispatches to the correct project CI:

```yaml
name: CI Router
on:
  push:
    branches: [main]
  pull_request:

jobs:
  detect:
    runs-on: ubuntu-latest
    outputs:
      tooling: ${{ steps.changes.outputs.tooling }}
      ios: ${{ steps.changes.outputs.ios }}
      core: ${{ steps.changes.outputs.core }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: changes
        with:
          filters: |
            tooling: 'tooling/**'
            ios: 'ios/**'
            core: 'web/packages/core/**'

  tooling:
    needs: detect
    if: needs.detect.outputs.tooling == 'true'
    uses: ./.github/workflows/tooling-ci.yml

  ios:
    needs: detect
    if: needs.detect.outputs.ios == 'true'
    uses: ./.github/workflows/ios-ci.yml

  core:
    needs: detect
    if: needs.detect.outputs.core == 'true'
    uses: ./.github/workflows/core-ci.yml
```

**Publish workflows** are also per-project, triggered by release events and filtered by tag pattern:

Example (`tooling/.github/workflows/publish.yml`):
```yaml
name: Tooling Publish
on:
  workflow_call:
    inputs:
      tag:
        required: true
        type: string
jobs:
  publish:
    if: startsWith(inputs.tag, 'tooling@v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
      - run: cd tooling && uv build && uv publish
```

The router's publish section dispatches on `release.published` events:

```yaml
  on-release:
    if: github.event_name == 'release'
    # ... dispatch to correct publish workflow based on tag prefix
```

**Sync** copies project workflows to the root:
- `tooling/.github/workflows/ci.yml` -> `.github/workflows/tooling-ci.yml`
- `tooling/.github/workflows/publish.yml` -> `.github/workflows/tooling-publish.yml`
- Regenerates `.github/workflows/ci-router.yml` from the workspace manifest

**On extraction to own repo:** Move `tooling/.github/workflows/ci.yml` to `.github/workflows/ci.yml`, change `workflow_call` trigger to `push`/`pull_request`, remove the `cd tooling &&` prefix from commands. The workflow logic is unchanged.

## Commands

### `rlsbl monorepo init`

Creates `.rlsbl-monorepo/workspace.json` with an empty projects array. Fails if already exists.

### `rlsbl monorepo add <path> [--name <name>]`

1. Validates the path exists.
2. Adds `{ "path": "<path>", "name": "<name>" }` to `workspace.json`. Name defaults to `os.path.basename(path)`.
3. Runs `rlsbl scaffold` inside the project directory (detects target, creates `.rlsbl/config.json`, `CHANGELOG.md`, CI workflows).
4. Runs `rlsbl monorepo sync` to update the router.

### `rlsbl monorepo remove <path>`

1. Removes the project from `workspace.json`.
2. Removes the copied CI workflows from `.github/workflows/`.
3. Runs `rlsbl monorepo sync` to regenerate the router.
4. Does NOT delete the project directory or its `.rlsbl/` config.

### `rlsbl monorepo sync`

1. Reads `workspace.json`.
2. For each project:
   - Copies `{path}/.github/workflows/ci.yml` -> `.github/workflows/{name}-ci.yml`
   - Copies `{path}/.github/workflows/publish.yml` -> `.github/workflows/{name}-publish.yml`
3. Generates `.github/workflows/ci-router.yml` from the manifest.
4. Warns about projects missing CI workflows (not yet scaffolded).
5. Removes stale workflows for projects no longer in the manifest.

Idempotent. Safe to run multiple times.

### `rlsbl monorepo status`

For each project in the workspace:
- Project name and path
- Detected target
- Current version
- Latest tag (if any)
- Whether CI workflows are synced (present at root)
- Whether CHANGELOG has unreleased entries

Table output:
```
Project    Path                   Target  Version  Tag              Synced  Unreleased
tooling    tooling/               pypi    0.1.0    tooling@v0.1.0   yes     2 entries
ios        ios/                   swift   1.0.0    (none)           yes     0 entries
core       web/packages/core      npm     0.1.0    (none)           no      1 entry
```

### `rlsbl monorepo list`

Simple list of projects with paths:
```
tooling    tooling/
ios        ios/
core       web/packages/core/
svelte     web/packages/svelte/
android    android/
spec       spec/
```

## Release Flow Changes

### Scoped Release

When `rlsbl release` runs inside a monorepo project (detects `.rlsbl-monorepo/workspace.json` by walking up from cwd):

1. Reads the project's own version from its manifest (pyproject.toml, Package.swift, etc.)
2. Bumps version, updates CHANGELOG.md (both in the project directory)
3. Commits with message: `{name}: release v{version}`
4. Tags with `{name}@v{version}` (not `v{version}`)
5. Pushes tag and commit
6. Creates GitHub Release titled `{name}@v{version}`

The tag prefixing is automatic -- the project doesn't need to configure it. rlsbl detects monorepo mode and reads the project's `name` from the workspace manifest.

### Standalone Release (no monorepo)

Unchanged. Tags remain `v{version}`. No prefix, no workspace lookup.

## Implementation Plan

### Phase 1: Workspace Foundation
- Create `.rlsbl-monorepo/` config directory convention
- `rlsbl monorepo init` command
- `rlsbl monorepo add` with auto-scaffold
- `rlsbl monorepo remove`
- `rlsbl monorepo list`
- Workspace manifest parsing

### Phase 2: Tag Prefixing
- Detect monorepo context (walk up to find `.rlsbl-monorepo/workspace.json`)
- Resolve current project's name from manifest
- Wrap `tag_format()` with prefix in release command
- Update GitHub Release title

### Phase 3: CI Sync
- `rlsbl monorepo sync` command
- Copy per-project workflows to root
- Generate router workflow from manifest
- Stale workflow cleanup

### Phase 4: Status and Polish
- `rlsbl monorepo status` command
- Warnings for un-synced projects
- Changelog unreleased detection
- Documentation

### Phase 5: Scaffold Awareness
- `rlsbl scaffold` inside a monorepo project generates reusable workflow format (`workflow_call`) instead of direct triggers
- Workflow includes `cd {path} &&` prefix in commands
- Generates both ci.yml and publish.yml
