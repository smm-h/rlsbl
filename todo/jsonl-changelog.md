# JSONL changelog source of truth

## Problem

Changelog entries are currently written as freeform Markdown in CHANGELOG.md. There is no structured mapping between changelog entries and commits. At release time, the human (or AI agent) must manually review `git log`, decide which commits are user-facing, and write descriptions. This is error-prone: commits get missed, internal changes leak into changelogs, and many-commits-one-change relationships are lost.

## Proposal

Split the changelog into two files:

- `CHANGELOG.jsonl` — structured source of truth, one JSON object per line
- `CHANGELOG.md` — generated by rlsbl at release time from the JSONL

Each JSONL entry maps a changelog description to one or more commit hashes:

```jsonl
{"description": "Session trailers for AI agent traceability", "commits": ["d7f2ce1"], "user_facing": true, "type": "feature"}
{"description": "File paths from subdirectories", "commits": ["f8abbc3", "ca45ed8"], "user_facing": true, "type": "fix"}
{"description": "selfdoc integration and config", "commits": ["9488320", "c3cbae2", "b50f9ec"], "user_facing": false}
{"commits": ["020c407"], "user_facing": false}
```

### Schema

- `commits` (required): array of short commit hashes
- `user_facing` (required): boolean
- `description` (required if `user_facing: true`, optional otherwise): one-line user-facing description
- `type` (required if `user_facing: true`): one of `feature`, `fix`, `breaking`

### Validation at release time

rlsbl must verify before releasing:

1. Every hash resolves (`git cat-file -t <hash>` succeeds)
2. Every hash is in the unreleased range (`origin/main..HEAD`)
3. Every unreleased commit appears in at least one entry (coverage)
4. No orphan hashes (catches stale entries from amended commits)
5. Every `user_facing: true` entry has `description` and `type`

### CHANGELOG.md generation

rlsbl generates the Markdown from JSONL entries where `user_facing: true`, grouped by `type`, using the existing changelog style of the project. The generated file should have a header comment indicating it is generated.

### Why JSONL

- Line-oriented: atomic appends, no need to parse the whole file
- Strict parsing with native arrays and optional fields
- Schema evolution: add a key with a default, no migration needed
- AI agents are the primary writers; JSON is native to LLMs

## Affected code

- `rlsbl release` — add JSONL validation step, generate CHANGELOG.md before committing
- `rlsbl status` — report JSONL coverage (unreleased commits mapped vs unmapped)
- Scaffold templates — add empty CHANGELOG.jsonl to new projects

## Migration

Existing projects keep their hand-written CHANGELOG.md. The JSONL workflow is opt-in: if `CHANGELOG.jsonl` exists, rlsbl uses it and generates the MD. If not, the current manual workflow continues.

## Effort

Medium. The core is JSONL parsing, commit validation, and MD generation. The validation logic is the bulk of the work.
